# Stage 2.1 Mutation Value Eval — 설계 (평가 기준 고정)

- 작성: 2026-11-11 · 외부 리뷰(Stage 2.0 심사·2.1 설계)를 그대로 옮기고, 실행에 필요한 선택 규칙을 **결과를 보기 전에** 정했다
- 근거: [보고서 #13](eval/20261111_eval_report_13.md), [design_stage2_0.md](design_stage2_0.md)
- 원칙: 코드는 `spikes/` 아래에 둔다. **`releaseguard/decide.py`는 바꾸지 않는다.** 에이전트 API 호출 없음.

## 1. 목표

KILLED 비율을 올리는 것이 아니다. 목표는 **기존 검증 공백 보고서(줄·분기 coverage)에서 보이지 않던 실제 테스트 부족을, 적은 추가 비용으로 찾을 수 있는지** 입증하는 것이다.

```text
Mutation의 추가 가치 = mutation이 찾은 유효한 검증 부족 − 기존 coverage로 이미 알 수 있던 부족
```

실제로 셀 값: 줄·분기 coverage가 공백으로 표시하지 않았던 위치 중, mutation으로 검증 부족이 **확인된** 수.

## 2. 어댑터 보완 (리뷰 3장)

| 항목 | 2.0 | 2.1 |
|---|---|---|
| 수집 오류 (pytest rc 2) | KILLED (`collection`) | **`COLLECTION_ERROR`로 분리**. 유효한 KILLED에 넣지 않는다 (기준 실행은 통과했으므로 mutant가 import를 깨뜨린 것) |
| 선택 실행 vs 전체 | 상태만 비교 | **상태 · 실패 종류 · 실패한 테스트 id**를 모두 비교. 선택 실행의 실패 id = 전체 실행의 실패 id ∩ 선택한 테스트일 때만 "완전 일치" |
| 격리 | 같은 스냅샷에서 적용·복구 | **mutant마다 원본 스냅샷을 새로 복사**한 폴더에서 실행하고, `try/finally`로 지운다. 스냅샷이 1MB 미만이라 비용이 작다. 테스트가 만든 파일이 다음 mutant에 남지 않는다 |

## 3. SURVIVED 분류 기준

| 분류 | 판단 기준 | 행동 |
|---|---|---|
| `ACTIONABLE_GAP` | 요구사항상 의미 있는 변화이고, 새 테스트가 원본에서는 PASS·mutant에서는 FAIL | 테스트 개선 후보 |
| `MEANINGFUL_UNVERIFIED` | 의미 있는 동작 변화가 예상되지만 테스트로 입증하지 못함 (시도하지 않음 포함) | 추가 조사 |
| `LOW_VALUE` | 변화는 있지만 프로젝트 계약상 검증 우선순위가 낮음 | 후순위 |
| `EQUIVALENT_SUPPORTED` | 정의된 입력 영역에서 동작이 같다는 충분한 근거가 있음 | 제외 후보 |
| `UNRESOLVED` | 위 어느 것으로도 분류할 증거가 부족함 | 미확정 |

- 잘못 만들어진 mutant나 실행 실패는 `INVALID` / `EXECUTION_ERROR` / `COLLECTION_ERROR`로 따로 둔다.
- 테스트 몇 개가 같은 결과를 냈다는 것만으로 `EQUIVALENT_SUPPORTED`라고 하지 않는다.

**`ACTIONABLE_GAP` 조건 (셋 다 만족)**:
1. **명세 근거**: 기대 동작이 왜 맞는지를 코드·테스트 목적·문서(`docs/decisions.md`, README) 또는 후속 결함 수정으로 설명할 수 있다.
2. **차등 테스트**: 새 테스트가 원본에서 PASS, mutant에서 FAIL이다.
3. **의미 있는 검증**: 실패가 실행 환경 문제나 인위적인 감지가 아니라, 동작에 대한 assertion에서 나온다.

**오라클 주의**: 원본 PASS·mutant FAIL이라고 해서 테스트의 기대 결과가 맞는 것은 아니다. Stage 1.6 F1에서 잘못된 동작을 정답으로 고정한 사례가 있었다. 그래서 조건 1의 근거를 기록에 함께 남긴다.

**증거 상태**: 분류마다 `confirmed`(테스트로 입증) / `plausible`(근거는 있으나 미입증) / `unresolved`를 따로 적는다. 테스트를 시도하지 않은 SURVIVED는 실패로 세지 않는다.

**분류자**: Claude 초안 → 사용자 확인. 기록에 `classified_by`를 남긴다.

## 4. 평가 A — 탐색: 2.0의 SURVIVED 13개 전수

13개를 하나도 빼지 않고 분류한다 (#7처럼 가치가 낮아 보이는 것 포함). 이미 결과를 본 집합이므로 **사전 등록 평가가 아니다**.

확인할 것:
- 계약상 의미 있는 변형이 몇 개인가
- 테스트 부족을 실제로 증명할 수 있는 변형이 몇 개인가
- 불필요한 검토의 원인
- 같은 위치의 결함(SZZ)과 연결되는 변형이 있는가

## 5. 평가 B — 확인: SZZ 결함 줄 vs 대조군 (새 mutant)

### 5.1 후보 풀

`out/eval/v14/20261107_szz.json`에서 결함 줄 161개 중 `covered`인 41개를 쓴다.

### 5.2 수기 결함 확인 (mutant를 만들기 전)

각 후보 줄의 후속 수정 커밋 diff와 메시지를 읽는다. 결함 확인으로 보는 조건은 둘 다다.
- 수정이 **그 줄의 동작**을 바꿨다 (단순 리팩터·이름 변경·포맷이 아님)
- 그 변경이 커밋 메시지에 적힌 결함과 연결된다

확인 결과는 `confirmed_defect` / `not_defect` / `unclear`이고, `confirmed_defect`만 쓴다. SZZ의 오추적(예: `99309f2` 라벨 충돌)이 있을 수 있으므로 이 단계를 생략하지 않는다.

### 5.3 선정 규칙 (고정)

1. 확인된 결함 줄 중 **허용 연산자(2.0과 같음)가 적용되는 줄**만 남긴다.
2. 결함을 들여온 커밋을 오래된 순으로 돌며 **커밋마다 한 줄씩** 고른다. 그 커밋 안에서는 파일 경로·줄 번호 순 첫 줄이고, 이미 고른 함수는 건너뛴다. 한 바퀴가 끝나면 다시 돈다. **최대 6줄**에서 멈춘다. 6줄이 안 되면 확보한 수만 보고한다.
3. 줄마다 mutant는 **최대 2개**, 연산자 이름 순으로 앞의 2개다.
4. **대조군**: 고른 결함 줄마다 1줄씩 짝을 짓는다.
   - 조건: 같은 커밋에서 바뀐 covered 줄이고, SZZ 결함 줄(상태와 관계없이)이 아니며, 같은 연산자 계열(비교 / 불리언 / 상수)이 적용된다.
   - 찾는 순서: 같은 파일에서 결함 줄 다음 줄부터 아래로, 없으면 위로, 없으면 같은 커밋의 다른 파일(경로 순)이다. 없으면 짝 없음으로 기록한다.
   - 대조군도 mutant는 최대 2개다. 대조군은 결함이 없다고 증명된 집합이 아니라, **알려진 후속 수정이 없는** 비교 집합이다.
5. 2.0에서 이미 만든 mutant(같은 커밋·줄·연산자)는 빼고 다음 연산자로 넘어간다.

선정 결과(커밋·줄·연산자·순서·제외 이유)는 mutant를 실행하기 전에 `eval/mutation_cases_2_1.yaml`에 커밋으로 고정한다. 실행 뒤에 바꾸지 않는다.

## 6. 테스트 추가 실험

**대상 선정 (고정)**:
- 평가 A에서 `MEANINGFUL_UNVERIFIED`로 분류된 SURVIVED를 mutant 번호 순으로, **커밋마다 1개씩, 최대 5개** 고른다.
- 평가 B의 SURVIVED는 결함 줄에서 1개를 더한다 (있으면, 결함 줄 선정 순서로 첫 번째).
- 합이 4개보다 적으면 평가 A의 `UNRESOLVED`를 mutant 번호 순으로 채운다.
- 고른 대상은 **모두 결과를 보고한다**. 실패한 시도도 포함한다.

**절차**:
1. 기대 동작의 근거(명세)를 먼저 적는다.
2. 테스트를 쓴다. 대상 커밋 스냅샷의 기존 테스트 파일 옆에 새 파일로 쓰고, Predict 저장소에는 넣지 않는다. 테스트 코드는 `docs/eval/v21/tests/`에 보관한다.
3. 원본 스냅샷과 mutant 스냅샷에서 각각 실행한다.

| 결과 | 해석 |
|---|---|
| 원본 PASS / mutant FAIL | 감지. 명세 근거까지 있으면 `ACTIONABLE_GAP` (confirmed) |
| 원본 PASS / mutant PASS | 감지 못 함 |
| 원본 FAIL | 테스트나 원본 동작 문제 → 따로 조사 |
| 실행 불가 | 환경·fixture·의존성 문제 |
| assertion 없이 예외만 | 유효한 검증인지 따로 판단 |

**기록**: 작성자(Claude, 사용자 개입 여부), 시도 횟수(수정 횟수), 기존 fixture·헬퍼 재사용 여부.
작성 시간은 사람 기준 검토 비용과 다르므로, 분 단위로 재지 않고 시도 횟수로 대신한다.

## 7. 지표

| 지표 | 정의 |
|---|---|
| Actionable Survivor Rate | `ACTIONABLE_GAP`(confirmed) / 검토한 SURVIVED. 분모를 "테스트를 시도한 SURVIVED"로 한 값도 함께 |
| Meaningful Mutation Rate | 의미 있는 변형(`ACTIONABLE_GAP` + `MEANINGFUL_UNVERIFIED`) / 전체 mutant |
| Incremental Detection | `ACTIONABLE_GAP` 중 그 줄이 줄 공백도 분기 공백도 아니었던 수 (coverage가 못 본 것) |
| Test Improvement Success | 감지 성공 / 시도한 테스트 |
| Review Cost | SURVIVED 하나를 분류하는 데 읽은 자료(파일·커밋 수). 유용한 사례 하나당 검토한 SURVIVED 수 |
| Execution Cost | mutant당 실행 시간 (선택 실행·전체) |
| SZZ vs Control | 결함 줄과 대조군 각각의 SURVIVED 비율과 `ACTIONABLE_GAP` 수 |

## 8. Go / Hold / No-Go (고정)

| 결정 | 기준 |
|---|---|
| **GO** — 2.2 통합 검토 | **서로 다른 커밋**에서 나온 confirmed `ACTIONABLE_GAP`이 **2건 이상**이고, 그중 coverage 대비 추가 정보(Incremental Detection)가 1건 이상이며, 실행 비용이 관리 가능 (mutant당 전체 실행 중앙값이 2.0과 같은 자릿수) |
| **HOLD** — 추가 실험 | 가치는 보이지만 한 커밋·한 연산자에 몰려 있거나, 검토 비용·실행 안정성이 불확실 |
| **NO-GO** — 2b로 | 의미 있는 추가 검증 부족이 확인되지 않거나, 불필요한 변형의 검토 비용이 지나치게 큼 |

이 숫자들은 통계적 성능 목표가 아니라 통합을 검토하기 위한 최소 근거다. GO여도 판정(SAFE·REVIEW·BLOCK)에 바로 연결하지 않는다. 2.2는 선택적 실행과 별도의 `mutation_result` 보고서부터 시작한다.
