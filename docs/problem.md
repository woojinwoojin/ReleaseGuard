# 문제 정의 (Stage 1 MVP)

작성: 2026-11-03 · 원본 제안서: `docs/proposal.md`

## 한 문장

개인 개발자가 **브랜치를 머지하기 직전**에, 이 변경이 **어떤 파일·기능에 영향을 주고 어떤 테스트로 검증해야 하는지**를 근거와 함께 알려준다.

## 범위

| 항목 | Stage 1 결정 |
|---|---|
| 사용자 | 개인 개발자 (본인) |
| 사용 시점 | PR 생성 전 또는 머지 직전, 직접 실행 |
| 형태 | 로컬 CLI |
| 입력 | 로컬 저장소 경로 + 기준 ref + 대상 ref (`git diff base...head`) |
| 첫 분석 대상 | `Predict_Success` (커밋 35개, `src/<모듈>` ↔ `tests/test_<모듈>.py` 구조) |
| 보조 대상 | 1~4주차 저장소 |
| Release Recommendation | SAFE / REVIEW REQUIRED / BLOCK — **규칙으로만 판정**, LLM은 근거 설명만 |

## 이번 범위에서 하지 않는 것

- GitHub PR API 연동, PR 코멘트 작성 (Stage 5)
- 테스트 실행 (Stage 2)
- 문서 RAG, 과거 장애 메모리 (Stage 3~4)
- merge·deploy 등 상태 변경 작업 일체

## 성공 기준 (제안서 19장 그대로)

1. 실제 Git 저장소를 분석할 수 있다.
2. diff에서 주요 변경사항을 추출할 수 있다.
3. 관련 코드와 테스트를 탐색할 수 있다.
4. 근거와 함께 주요 위험을 설명할 수 있다.
5. 필요한 테스트를 추천할 수 있다.
6. 동일 입력에 대해 크게 불안정하지 않은 결과를 낸다.
7. 결과가 어떤 evidence에서 나왔는지 추적할 수 있다.
8. Eval Set으로 성능을 반복 측정할 수 있다.
