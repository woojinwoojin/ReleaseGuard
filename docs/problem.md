# 문제 정의 v2 (Stage 1 MVP)

작성: 2026-11-03 · 원본 제안서: `docs/proposal.md` · v1은 이 문서의 git 기록 참고

## 한 문장

개인 개발자가 **브랜치를 머지하기 직전**에, 이 변경으로 바뀐 코드 중 **어떤 테스트도 실행하지 않는 부분(검증 공백)**을 찾고, 이 변경을 실행하는 테스트를 **실제로 돌려** 결과와 함께 알려준다.

## 답하는 질문

| # | 질문 | 방식 |
|---|---|---|
| Q1 | 이 변경을 실행하는 테스트는 무엇인가 | 테스트 실행 + 줄 단위 coverage (결정적) |
| Q2 | 바뀐 줄 중 어떤 테스트도 실행하지 않는 곳은 어디인가 | coverage와 diff 대조 (결정적) |
| Q3 | 그 테스트들은 통과하는가 | 테스트 실행 (결정적) |
| Q4 | 검증 공백마다 어떤 동작이 바뀌었고, 어떤 테스트가 필요한가 | 에이전트 — 공백 하나씩, 좁은 질문 |

판정(SAFE / REVIEW REQUIRED / BLOCK)은 Q1~Q3의 결정적 결과로만 정한다. 에이전트(Q4)는 판정에 들어가지 않고 설명과 테스트 제안만 한다.

## 범위

| 항목 | 결정 |
|---|---|
| 사용자 | 개인 개발자 (본인) |
| 사용 시점 | PR 생성 전 또는 머지 직전, 직접 실행 |
| 형태 | 로컬 CLI |
| 입력 | 로컬 저장소 경로 + 기준 ref + 대상 ref (`git diff base...head`) |
| 테스트 실행 위치 | 대상 커밋을 임시 worktree로 꺼내서 실행 (사용자 작업 폴더를 건드리지 않음) |
| 시험장 | Predict_Success (데이터 파이프라인, 커밋 35개, 테스트 182개), 4주차 Docker_UI_CI (API·DB·Docker·CI, 커밋 9개) |

## 이번 범위에서 하지 않는 것

- **결함 탐지(코드 리뷰)**: "이 코드가 틀렸는가"는 판단하지 않는다. 테스트가 *실행*하는지만 본다.
- 테스트가 *검증*까지 하는지 (assert의 강도, mutation testing) — 이후 단계
- LLM이 판정에 관여하는 것
- GitHub PR API, PR 코멘트, merge·deploy 등 상태 변경 작업
- Python 외 언어

## 성공 기준

1. 대상 커밋을 임시 worktree로 꺼내 테스트와 coverage를 실행하고, 사용자 작업 폴더는 바뀌지 않는다.
2. 바뀐 줄마다 그 줄을 실행한 테스트 목록이 나온다 (Q1).
3. 검증 공백(바뀐 실행 줄 중 아무 테스트도 실행하지 않는 줄)이 파일·줄 범위로 나온다 (Q2).
4. 테스트 실패가 있으면 BLOCK이고, 실패한 테스트와 오류 위치가 나온다 (Q3).
5. 같은 입력에서 판정·공백·테스트 목록이 실행마다 같다.
6. 결함을 심은 사례에서 공백·실패를 빠짐없이 잡는다.
7. SZZ 라벨로 "결함을 들여온 커밋"에서 검증 공백이 있었는지 잴 수 있다.
8. 모든 결과가 근거(coverage 줄, 테스트 id, 실행 로그)로 추적된다.
