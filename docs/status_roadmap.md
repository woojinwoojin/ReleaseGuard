# ReleaseGuard — 현재 상태와 로드맵

기준일: 2026-11-03 · 버전 0.2.0 · 테스트 74개 통과

## 1. 한 줄 소개

**머지하기 전에, 바뀐 코드 중 어떤 테스트도 실행하지 않는 곳(검증 공백)을 찾고, 테스트를 실제로 돌려서 SAFE / REVIEW REQUIRED / BLOCK으로 알려주는 로컬 CLI.**

코드가 *맞는지*는 판단하지 않는다. "무엇이 검증됐고 무엇이 검증되지 않았는가"를 근거와 함께 보여준다.

## 2. 지금 할 수 있는 것

```powershell
.\.venv\Scripts\python -m releaseguard analyze --repo ..\predict-success --base main --head my-branch
```

이 명령 하나로:

1. 바뀐 파일과 줄을 모은다.
2. 대상 커밋을 **임시 폴더에 꺼내** 테스트 전체를 coverage와 함께 돌린다. 사용자의 작업 폴더는 건드리지 않는다.
3. 바뀐 줄마다 **어떤 테스트가 실행했는지**, 어떤 줄은 **아무 테스트도 실행하지 않았는지** 표시한다.
4. 테스트가 실패하면 base에서 다시 돌려 **"이번 변경이 깨뜨렸나 / 원래 깨져 있었나"**를 구분한다.
5. 규칙으로 판정한다 (LLM은 판정하지 않음).
6. (선택) 공백마다 에이전트가 "무엇이 바뀌었고 어떤 테스트를 추가하면 되는지" 제안한다.
7. JSON(근거 포함)과 Markdown 보고서를 저장한다. 예: [samples/report_142912b.md](samples/report_142912b.md)

판정 기준:

| 판정 | 언제 |
|---|---|
| **BLOCK** | 비밀값 노출(B01), 이번 변경으로 테스트 실패(B03), 테스트 수집 오류(B04) |
| **REVIEW REQUIRED** | 검증 공백(G01), 원래 깨진 테스트(T01), 의존성 변경(R04), 테스트를 못 돌림(E01) |
| **SAFE** | 위에 해당 없음 — 테스트 통과, 바뀐 실행 줄 모두 테스트가 실행 |

설정·데이터 변경은 판정에 넣지 않고 "참고"로만 보여준다.

## 3. 동작 흐름

```text
base...head
   │
   ▼
[1 Collect]  git diff → 바뀐 파일·줄
   │
[2 Classify] 규칙 → source / test / config / docs / data / deps, 비밀값 검사
   │
[3 Run]      git archive → 임시 폴더 → pytest + coverage (테스트별 실행 줄 기록)
   │          └ 실패 테스트만 base에서 재실행
[4 Gaps]     바뀐 실행 가능 줄 − 테스트가 실행한 줄 = 검증 공백
   │
[5 Decide]   판정 규칙 v2 (결정적)
   │
[6 Explain]  (선택) 공백마다 에이전트: 바뀐 동작 + 제안 테스트 — 판정에는 안 들어감
   │
[7 Report]   JSON + Markdown
```

## 4. 구현된 범위

| 영역 | 기능 | 상태 | 파일 |
|---|---|---|---|
| 수집 | merge-base 기준 변경 파일·줄, 이름 변경, 추가된 줄 | 완료 | `git_ops.py` |
| 분류 | 7가지 분류 규칙(YAML), 비밀값 패턴 5종 | 완료 | `classify.py`, `configs/rules.yaml` |
| 실행 | 스냅샷 실행, 대상 `.venv` 사용, coverage 별도 공급, 테스트별 실행 줄, 시간 상한·재시도, base 재실행 | 완료 | `runner.py` |
| 공백 | 줄 상태 4종(covered / import_only / gap / not_executable), 범위 묶기 | 완료 | `gaps.py` |
| 판정 | 규칙 v2 (BLOCK 3, REVIEW 4, NOTE 3) | 완료 | `decide.py` |
| 설명 | 공백당 좁은 질문 에이전트, 읽기 전용 도구 4개, 근거·테스트 경로 검증 | 완료 (평가는 1회뿐) | `agent.py`, `agent_tools.py` |
| 대체 | 테스트를 못 돌릴 때 이름·import로 관련 테스트 추정 | 완료 | `related_tests.py` |
| 보고서 | 판정 근거, 테스트 결과, 줄별 검증 상태, 공백 설명 | 완료 | `report.py` |
| 평가 | 커밋 전체 평가·결정성, 결함 심은 사례, SZZ | 완료 | `evaluate.py`, `eval/*.yaml` |
| CLI | `analyze`, `eval`, `seeds`, `szz` | 완료 | `__main__.py` |

하지 않는 것 (의도적으로 범위 밖): GitHub PR 연동, merge·배포, Python 외 언어, 테스트 선택 실행, 샌드박스.

## 7. 알려진 한계

1. **"실행됐다" ≠ "확인됐다"**: 나중에 고쳐진 결함 줄의 41%는 테스트가 실행했는데도 결함이 남았다. 지금은 assert의 강도를 보지 않는다.
2. **Docker·CI 변경은 검증하지 못한다** (심은 사례 W05·W06).
3. **G01이 자주 발동한다**: Predict_Success 커밋의 56%가 공백 때문에 REVIEW. 공백 1줄과 100줄이 같은 판정이다.
4. **대상 저장소의 테스트 코드를 그대로 실행한다**: 신뢰하는 저장소에만 써야 한다 (샌드박스 없음).
5. Python + pytest 저장소만, 대상 `.venv`의 Python이 3.13이어야 한다 (coverage 버전 맞춤).
6. 공백 설명 에이전트는 실제 API로 1회만 평가했다.
7. 수기 라벨 15개는 v1 기준으로 달았다.

### 이후 단계 (제안서 Stage 2~7을 이번 결과에 맞춰 조정)

각 단계는 **앞 단계의 Eval에서 근거가 확인될 때만** 시작한다.

| Stage | 내용 | 시작 근거 (지금까지 확인된 것) | 로드맵 연결 |
|---|---|---|---|
| **2. 확인 강도** | 바뀐 줄에 한정한 mutation testing — "이 줄을 바꿔도 테스트가 실패하나?" | 결함 줄 41%가 실행됐는데도 남음 (SZZ) | 1년 로드맵 2번 (agent·tool·workflow) |
| **2b. 배포 산출물 검증** | Dockerfile·compose·CI 변경 시 `docker build`, 워크플로 문법·필수 단계 검사 | W05·W06 실패 | 1번에서 만든 Docker·CI 경험 재사용 |
| **2c. Workflow 엔진** | 실행 → 재시도 → 분기(테스트 실패 시 base 재실행, mutation) 흐름이 늘면 LangGraph 검토 | 지금은 직선 흐름이라 불필요 | 2번 |
| **3. Knowledge RAG** | 대상 저장소의 원칙·결정 문서(예: `decisions.md`)를 검색해 공백 설명·우선순위에 사용 | Eval #2: 결함이 "원칙 위반"형이고 에이전트가 원칙을 몰라 오판 | 3번 (RAG·임베딩) |
| **4. Experience Memory** | SZZ로 찾은 과거 결함 줄·파일을 저장 → 같은 곳이 바뀌면 "과거 결함 위치" 표시 | SZZ로 결함 줄 161개를 이미 추적 가능 | 2·3번 |
| **5. GitHub 연동** | GitHub Action으로 PR마다 실행, PR 코멘트. MCP는 외부 도구가 늘 때 | 로컬 CLI가 안정화된 뒤 | 5번 (CI/CD) |
| **6. Multi-Agent** | 실행·확인·설명이 독립적으로 커지고 병렬 효과가 측정될 때만 | 아직 없음 | 4번 |
| **7. 운영** | 실행 기록 수집(Langfuse 등), 사용자 override 기록, 실패 사례를 Eval에 추가 | 아직 없음 | 5번 |
