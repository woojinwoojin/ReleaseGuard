# ReleaseGuard — 현재 상태와 로드맵

기준일: 2026-11-04 · 버전 0.2.0 · 판정 규칙 v3 · 테스트 87개 통과

## 1. 한 줄 소개

**머지하기 전에, 바뀐 코드 중 어떤 테스트도 실행하지 않는 곳(검증 공백)을 찾고, 테스트를 실제로 돌려서 SAFE / REVIEW REQUIRED / BLOCK으로 알려주는 로컬 CLI.**

코드가 *맞는지*는 판단하지 않는다. "무엇이 검증됐고 무엇이 검증되지 않았는가"를 근거와 함께 보여준다.

## 2. 지금 할 수 있는 것

```powershell
.\.venv\Scripts\python -m releaseguard analyze --repo ..\predict-success --base main --head my-branch
```

이 명령 하나로:

1. 바뀐 파일과 줄을 모은다.
2. 대상 커밋을 **임시 폴더에 꺼내** 테스트 전체를 coverage와 함께 돌린다. 사용자의 작업 폴더는 건드리지 않는다.
3. 바뀐 줄마다 **어떤 테스트가 실행했는지**, 어떤 줄은 **아무 테스트도 실행하지 않았는지** 표시한다.
4. 테스트가 실패하면 head에서 한 번, base에서 한 번 더 돌려 **불안정(FLAKY) / 이번 변경 후 실패 / 원래 깨짐 / 비교 불가 / 확인 불가**를 구분한다.
5. 규칙으로 판정한다 (LLM은 판정하지 않음).
6. (선택) 공백마다 에이전트가 "무엇이 바뀌었고 어떤 테스트를 추가하면 되는지" 제안한다.
7. JSON(근거 포함)과 Markdown 보고서를 저장한다. 예: [samples/report_142912b.md](samples/report_142912b.md)

판정 기준:

| 판정 | 언제 |
|---|---|
| **BLOCK** | 비밀값 노출(B01), 원래부터 실패했다고 확인되지 않은 테스트 실패(B03), 테스트 수집 오류(B04) |
| **REVIEW REQUIRED** | 검증 공백(G01), 원래 깨진 테스트(T01), 불안정한 테스트(T02), 의존성 변경(R04), 테스트를 못 돌림(E01), 검증 범위 밖 변경(E02: 설정·데이터·Docker·CI·Python이 아닌 소스), 스냅샷 예외(E03) |
| **SAFE** | 위에 해당 없음 — **ReleaseGuard의 검증 절차에서** 검토 사유를 찾지 못함 (코드가 맞다는 보증이 아님) |

판정과 별도로 **검증 범위**(COMPLETE / PARTIAL / UNSUPPORTED)와 검증하지 못한 파일 목록을 남긴다 (판정 규칙 v3, `docs/design.md`).

## 3. 동작 흐름

```text
base...head
   │
   ▼
[1 Collect]  git diff → 바뀐 파일·줄
   │
[2 Classify] 규칙 → source / test / config / docs / data / deps, 비밀값 검사
   │
[3 Run]      git archive → 임시 폴더 → pytest + coverage (테스트별 실행 줄 기록)
   │          └ 실패 테스트: head 재실행(FLAKY) → base 실행(비교 상태)
[4 Gaps]     바뀐 실행 가능 줄 − 테스트가 실행한 줄 = 검증 공백
   │
[5 Decide]   판정 규칙 v3 + 검증 범위 (결정적)
   │
[6 Explain]  (선택) 공백마다 에이전트: 바뀐 동작 + 제안 테스트 — 판정에는 안 들어감
   │
[7 Report]   JSON + Markdown
```

| 영역 | 기능 | 상태 | 파일 |
|---|---|---|---|

| 분류 | 7가지 분류 규칙(YAML), 비밀값 패턴 5종 | 완료 | `classify.py`, `configs/rules.yaml` |

| 공백 | 줄 상태 4종(covered / import_only / gap / not_executable), 범위 묶기, fixture에서만 실행된 줄, 분기 공백(판정 미반영) | 완료 | `gaps.py` |

## 7. 알려진 한계

1. **"실행됐다" ≠ "확인됐다"**: 나중에 고쳐진 결함 줄의 41%는 테스트가 실행했는데도 결함이 남았다. 지금은 assert의 강도를 보지 않는다.
2. **Docker·CI 변경은 검증하지 못한다** (심은 사례 W05·W06).
3. **G01이 자주 발동한다**: Predict_Success 커밋의 56%가 공백 때문에 REVIEW. 공백 1줄과 100줄이 같은 판정이다.
4. **대상 저장소의 테스트 코드를 그대로 실행한다**: 신뢰하는 저장소에만 써야 한다 (샌드박스 없음).
5. Python + pytest 저장소만, 대상 `.venv`의 Python이 3.13이어야 한다 (coverage 버전 맞춤).
6. 공백 설명 에이전트는 실제 API로 1회만 평가했다.
7. 수기 라벨 15개는 v1 기준으로 달았다.
8. **SAFE가 검증 범위를 넘어선다** (2026-11-04 외부 설계 리뷰 후 코드 대조로 확인):
   - 설정(Dockerfile·CI·yaml)·데이터만 바뀌면 NOTE만 남고 SAFE (`decide.py`). 4주차 Eval SAFE 6개 중 3개가 이 경우.
   - `.js`·`.sh`·`.sql`은 source로 분류되지만 공백 계산은 `.py`만 해서, 이것만 바뀌면 아무 표시 없이 SAFE (`gaps.py`).
9. **base 재실행이 실패하면 "이번 변경으로 실패"로 기록된다**: base 결과가 비면 `absent`로 처리 (`analyze.py`). 판정(BLOCK)은 보수적이지만 근거 문장이 사실과 다름.
10. head와 base를 같은 `.venv`로 실행한다. 의존성이 바뀐 커밋은 비교 조건이 다르다는 표시가 없다.
11. ~~fixture에서만 실행된 줄이 `import_only`로 분류된다~~ → 1.5에서 해소 (pytest-cov 단계 context, `fixture_only`).
12. ~~줄 단위 coverage만 쓴다~~ → 1.5에서 분기 공백을 따로 표시. **판정에는 넣지 않는다**: 분기 공백만 있는 커밋 0/58, SZZ covered 결함 줄 중 분기 공백 2/41 ([보고서 #6](eval/20261104_eval_report_6.md)). 분기에는 테스트 context가 없다.
14. **skip된 테스트는 판정에 들어가지 않는다**: 보고서에 목록·사유만 나온다. 새로 추가한 테스트가 전부 skip돼도 SAFE가 나올 수 있다.
15. **깨끗한 스냅샷이지 격리된 환경이 아니다**: 호스트 환경 변수(예: `OPENAI_API_KEY`)가 테스트에 그대로 넘어간다. 변수 이름만 기록한다.
16. **같은 실패 판단은 좁게 시작했다 (v3.1)**: 같은 파일의 헬퍼·다른 테스트가 바뀌면 실패한 테스트와 관련이 없어도 INCOMPARABLE(BLOCK). 관련성(테스트가 실제로 쓰는 헬퍼·fixture)은 아직 따지지 않는다.
13. Eval 지표 이름: "관련 테스트 0.861/0.969"는 실제 관련성이 아니라 **같은 커밋에서 바뀐 테스트 찾기(Changed-test Retrieval)**. SZZ 59% vs 전체 48%는 차이 11%p로 약한 연관 단서일 뿐.

## 8. 로드맵

### 다음 세션 (Stage 1 마무리 — 2026-11-04 외부 설계 리뷰 반영해 재정렬)

원칙: **SAFE는 "코드가 맞다"가 아니라 "정의된 검증 절차에서 검토 사유를 찾지 못했다"는 뜻.** 검증하지 못한 것을 검증한 것처럼 말하지 않는다.

| 순서 | Stage | 할 일 | 끝났다고 보는 기준 |
|---|---|---|---|
| 1 | 1.1 판정 의미 | `scope_status`(COMPLETE·PARTIAL·UNSUPPORTED)를 판정과 따로 기록. 검증하지 못한 변경이 있으면 SAFE 대신 REVIEW (E02, 결정: 방식 A). 문서만 바뀌면 COMPLETE + SAFE | 한계 8 해소, Eval 재실행으로 바뀐 판정 확인 (예상: Predict 0개, 4주차 3개) |
| 1 | 1.2 Runner 검증 | 실패 비교 상태 분리(REGRESSION·PRE_EXISTING·FLAKY·INCOMPARABLE·UNKNOWN), 실행 기록(명령·Python·SHA·timeout) 저장, 스냅샷 예외(export-ignore·서브모듈·LFS) 감지 | 한계 9·10 해소, 상태별 테스트 |
| 2 | 1.3 Eval 정비 | 수기 라벨 v2 기준 재정의(15개는 회귀용), 정상 변경·범위 밖 변경 사례 추가, 지표 이름 정정 | 라벨 기준 문서, 과잉 경고율을 따로 잼 |
| 3 | ~~1.5 Branch coverage~~ **완료** | `branch = True`, 바뀐 조건문의 실행 안 된 분기 표시(판정 미반영), pytest-cov로 테스트 단계 구분 | 한계 11·12 해소, 58커밋 판정 변화 0, 실행 시간 약 1/3 ([#6](eval/20261104_eval_report_6.md)) |
| 4 | 1.4 G01 우선순위 (**다음**) | 판정(REVIEW)은 그대로, 공백 크기·비율·구조(AST: 조건·예외·반환)·분기 누락으로 검토 순서 HIGH·MEDIUM·LOW. #6 관찰: G01 과잉 7개 중 3개는 파일 전체가 공백(실험 스크립트) — 구조 신호 후보 | 같은 Eval에서 결함 줄이 위쪽에 오고 G01 과잉 7개가 아래쪽에 오는지 비교 (REVIEW 비율 줄이기는 기준이 아님) |
| 5 | 1.6 에이전트 Eval | 근거 일치, 제안 테스트가 공백을 메우는지. 제안 테스트 자동 실행은 실행 격리 뒤로 | 근거 확인 비율, 공백 메움 비율 |
| 6 | — | 기술 블로그 (v1 실패 → v2 재설계) | 초안 1개 |
