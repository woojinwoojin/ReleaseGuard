## 1. 한 줄 소개

**머지하기 전에 바뀐 코드 중 어떤 테스트도 실행하지 않는 곳(검증 공백)을 찾는 로컬 CLI다. 테스트를 실제로 돌린 뒤 SAFE / REVIEW REQUIRED / BLOCK으로 알려준다.**

코드가 *맞는지*는 판단하지 않는다. "무엇이 검증됐고 무엇이 검증되지 않았는가"를 근거와 함께 보여준다.

**현재 제품 계약:** 1차 결과물은 변경 줄·분기의 검증 공백과 실행 근거를 담은 **보고서**다. SAFE / REVIEW REQUIRED / BLOCK은 검증 부족을 놓치지 않도록 설계한 **보수적 게이트**이며, 결함 확률 또는 코드 품질 순위가 아니다. 특히 코드 변경 커밋에서 이 판정이 검토 대상을 잘 구분한다는 근거는 아직 부족하다. 판정의 구분력 개선은 별도 측정 과제로 관리한다.

## 2. 지금 할 수 있는 것

```powershell
.\.venv\Scripts\python -m releaseguard analyze --repo ..\predict-success --base main --head my-branch
```

이 명령 하나가 하는 일:

1. 바뀐 파일과 줄을 모은다.
2. 대상 커밋을 **임시 폴더에 꺼내** 테스트 전체를 coverage와 함께 돌린다. 사용자의 작업 폴더는 건드리지 않는다.
3. 바뀐 줄마다 **어떤 테스트가 실행했는지**, 어떤 줄은 **아무 테스트도 실행하지 않았는지** 표시한다. 분기 공백은 참고로만 표시한다.
4. 테스트가 실패하면 head에서 한 번, base에서 한 번 더 돌려 실패를 구분한다: 불안정(FLAKY) / 이번 변경 뒤 실패 / 원래 깨짐 / 비교 불가 / 확인 불가.
5. 규칙으로 판정한다 (LLM은 판정하지 않음). 검증 범위(COMPLETE / PARTIAL / UNSUPPORTED)도 따로 기록한다.
6. (선택) 공백마다 에이전트가 "무엇이 바뀌었고 어떤 테스트를 추가하면 되는지" 제안한다. 제안은 결정적 규칙 S01~S03으로 한 번 더 검사한다.
7. JSON(근거 포함)과 Markdown 보고서를 저장한다. 공백은 함수별로 묶어 공백 줄이 많은 곳부터 보여준다 (결함 위험 순서가 아님).

판정 기준:

| 판정 | 언제 |
|---|---|
| **BLOCK** | 비밀값 노출(B01), 원래부터 실패했다고 확인되지 않은 테스트 실패(B03), 테스트 수집 오류(B04) |
| **REVIEW REQUIRED** | 검증 공백(G01), 원래 깨진 테스트(T01), 불안정한 테스트(T02), 의존성 변경(R04), 테스트를 못 돌림(E01), 검증 범위 밖 변경(E02: 설정·데이터·Docker·CI·Python이 아닌 소스), 스냅샷 예외(E03), 바뀐 테스트가 실행되지 않음(T03) |
| **SAFE** | 위에 해당 없음 — **ReleaseGuard의 검증 절차에서** 검토 사유를 찾지 못함 (코드가 맞다는 보증이 아님) |

## 3. 동작 흐름

```text
base...head
   │
   ▼
[1 Collect]  git diff → 바뀐 파일·줄
   │
[2 Classify] 규칙 → source / test / config / docs / data / deps, 비밀값 검사
   │
[3 Run]      git archive → 임시 폴더 → pytest + pytest-cov (테스트·단계별 실행 줄, 분기)
   │          └ 실패 테스트: head 재실행(FLAKY) → base 실행(비교 상태, v3.1)
[4 Gaps]     바뀐 실행 가능 줄 − 테스트가 실행한 줄 = 검증 공백 → 함수별 그룹
   │
[5 Decide]   판정 규칙 v3.2 + 검증 범위 + 바뀐 테스트 실행 확인(T03) (결정적)
   │
[6 Explain]  (선택) 공백마다 에이전트: 바뀐 동작 + 제안 테스트 → S01~S03 검사 — 판정에는 안 들어감
   │
[7 Report]   JSON + Markdown
```

## 7. 알려진 한계

1. **"실행됐다" ≠ "확인됐다"**: 나중에 고쳐진 결함 줄의 41%는 테스트가 실행했는데도 결함이 남았다. assert의 강도는 보지 않는다. 분기로도 설명되지 않는다 (covered 결함 줄 중 분기 공백은 2/41).
2. **Docker·CI 변경은 검증하지 못한다.** E02 REVIEW + UNSUPPORTED로 표시만 한다.
3. **G01 및 판정 구분력 부족**: 공백 1줄과 100줄이 같은 판정이다. `need: no` 전체에서는 11/19, 코드 변경만 보면 **11/12**에 경고가 발생했다. 코드 변경 41개 중 SAFE는 1개뿐이다. 1.4는 함수별로 정리했지만 경고 자체는 줄이지 않았다. 이 수치는 소규모·유사 저장소의 라벨 표본 결과이지 일반화된 오탐률이 아니다.
4. **대상 저장소의 테스트 코드를 그대로 실행한다**: 신뢰하는 저장소에만 써야 한다 (샌드박스 없음).
5. **깨끗한 스냅샷이지 격리된 환경이 아니다**: 호스트 환경 변수가 테스트에 그대로 넘어간다. 변수 이름만 기록한다.
6. Python + pytest 저장소만 지원하고, 대상 `.venv`의 Python은 3.13이어야 한다.
7. head와 base를 같은 `.venv`로 실행한다. 의존성이 바뀐 커밋은 R04로만 표시한다.
8. **바뀐 테스트 실행 확인(T03)의 범위**: 1.7에서 결과 없음·전부 skip·모듈 skip·테스트 전부 삭제를 T03으로 드러낸다. 남은 것:
   - 원래 skip이던 테스트도 구분 없이 경고해 같은 원인이 반복된다 (week3 6회). 판정은 그대로 두고 반복 원인으로만 기록한다. 묶어 보여주기는 나중 과제다.
   - `test*`가 아닌 이름으로 쓴 테스트(예: `test_x.py`의 `check_result()`)는 대상에서 빠져 T03 없이 SAFE가 될 수 있다. 헬퍼 파일 과잉 경고를 막으려고 고른 절충이다.
   - 삭제만 있는 테스트 함수 변경은 보지 않는다.
   - 미지원 수집 설정에서는 검사를 보류한다(N07).
   - 소스 삭제만 있으면 N06 NOTE로 SAFE다 (실행되지 않는 경로의 참조는 미검증, D3).
9. **같은 실패 판단이 좁다 (v3.1)**: 같은 파일의 헬퍼가 바뀌면, 실패한 테스트와 관련이 없어도 INCOMPARABLE(BLOCK)이 된다. 테스트가 실제로 쓰는 헬퍼인지는 따지지 않는다.
10. 공백 설명 에이전트는 skip 파일에 테스트를 넣자고 하거나, 이미 있는 테스트와 내용이 겹치는 테스트를 제안한다. S01·S03이 skip 파일과 이름 충돌은 잡지만 내용 중복은 못 잡는다. 평가는 실험당 8개 × 2회뿐이다.
11. 지표 이름: "바뀐 테스트 찾기 0.861/0.969"는 실제 관련성이 아니라 같은 커밋에서 바뀐 테스트를 찾은 비율이다. SZZ 59% vs 48%는 약한 연관 단서일 뿐이다.
12. **T03의 외적 타당성 미확인**: 심은 사례·통합 테스트로 고정했지만, 58커밋에서 이전에 SAFE였다가 바뀐 커밋은 0개다. 이 경계 입력이 있는 독립 저장소로 평가해야 한다.

해소된 한계 (기록용): 검증 범위 밖 변경의 SAFE(1.1), base 재실행 실패의 잘못된 근거(1.2), v1 기준 라벨(1.3), fixture 줄 `import_only` 분류(1.5), 줄 단위 coverage만 사용(1.5), 테스트만 바뀐 경계 사례의 SAFE(1.7), coverage 실제 버전 미확인·원본 node id 미보존(1.7).

| T03 (신규 REVIEW 후보) | 새·수정 테스트 파일에서 기대한 테스트가 0개 수집됨, 변경 테스트가 모두 skip됨, 마지막 테스트 삭제로 suite가 `no_tests`가 됨 | 각각 최소 1개 seed + 정상/혼합 테스트 반례. `no_tests` 소스 변경의 기존 G01 유지 |

**범위/판정 계약:** `scope`는 처리 가능한 변경 파일 범위에 대한 상태이고, `T03`은 실제 변경 테스트의 실행 근거가 부족하다는 별도 신호다. `COMPLETE`를 '모든 변경 테스트가 실행됨'으로 읽어서는 안 된다. scope 상태의 의미를 바꾸는 작업은 별도 스키마/평가 변경으로 취급한다.

**추가 추적 과제 — Decision Utility (판정 구분력):** 현재 규칙을 즉시 느슨하게 만들지는 않는다. `need: no`인 코드 변경 11/12에 경고하는 상태를 제품 한계로 명시하고, 문서 변경을 분리한 혼동행렬·경고 규칙별 원인·검토 시간·놓친 위험을 독립 저장소에서 재평가한다. Mutation이 이 문제를 해결한다는 가설은 세우지 않는다. 특히 Stage 2.2 정식 통합 전 제품 가치 지표에 해당 결과를 포함한다.
