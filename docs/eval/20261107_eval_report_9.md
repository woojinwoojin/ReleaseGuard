## 1. 결론

**가설 "실패는 입력 부족에서 나온다, 사실을 넣으면 나아진다"는 지지되지 않았다.**

- 핵심 지표 두 개가 그대로다. 건너뛴 테스트 목록을 받고도 N3·B1의 4회 모두 전체 skip 파일에 테스트를 제안했고, skip을 말한 응답은 16회 중 0회다.
- N3는 기존 테스트와 겹치는 상태가 그대로이고, 오히려 목록의 이름을 그대로 가져와 **같은 이름**을 제안했다. 그대로 넣으면 기존 테스트 함수를 덮어쓴다.
- 나빠진 것: 반복 일관성 16 → 12, 근거 참조 오류 0 → 2. 도구를 쓰지 않은 실행이 3회 → 6회로 늘었다.
- 좋아진 것은 비용뿐이다 ($0.2384 → $0.1885). 이것도 도구를 덜 쓴 결과라 좋은 일로만 볼 수 없다.

보고서 #8의 "실패는 입력 부족에서 나왔다"는 판단은 **틀렸거나 적어도 불충분했다.** 정보가 없는 것이 아니라, 정보가 있어도 지시 없이는 쓰지 않는다.

추천: **실험 2의 입력을 채택하지 않고 기준선을 유지한다.** skip 문제는 LLM에게 맡기지 않고, 결정적 코드로 처리한다 (4장).

## 3. 관찰

- **입력이 늘었는데 조사가 줄었다.** 도구 호출이 59 → 41이고, N3·B2는 두 번 다 도구를 안 썼다. 그 결과 B2는 저장소의 `read_sse`·fixture를 쓰지 않는 제안이 됐고, N3는 호출한 적 없는 `tool:#1`과 142줄 파일의 `1-200`을 근거로 적었다. 이유는 확인하지 못했다 (추측: 테스트 이름을 받아 더 찾을 필요가 없다고 판단).
- **좋아진 사례 하나**: F2 실행 1은 `guideline_section`을 직접 호출하도록 바뀌었다. 다만 입력에 이 함수의 기존 테스트가 없었으므로 입력 보강의 효과라고 볼 근거가 없다.
- **출력 품질 문제**: F1 실행 1의 설명에 다른 언어 단어가 한 개 섞였다.
- 일관성 하락이 입력 때문인지 우연인지는 구분할 수 없다. 실험 1의 응답도 두 번만 돌렸고, 같은 조건의 변동 폭을 재지 않았다.

## 4. 다음 선택

프로토콜대로 프롬프트나 모델을 바로 키우지 않고 원인부터 나눈다.

| 문제 | 원인으로 확인된 것 | 추천 |
|---|---|---|
| skip 파일에 테스트 제안 | 입력이 없어서가 아님 (입력을 줘도 같음) | **결정적 코드로 처리**: 제안 파일에 skip이 있으면 보고서에 경고 |
| 공백의 원인이 skip | 에이전트가 말하지 않음 | **결정적 코드로 처리**: skip 사유와 공백을 보고서에서 연결 |
| 기존 테스트와 같은 이름 | 코드로 검사 가능 | **결정적 코드로 처리**: 이름 충돌 경고 |
| 없는 참조 인용 | 이미 코드가 잡음 (`references_valid`) | 현재 검사 유지 |

세 가지 모두 LLM 없이 항상 같은 결과를 낼 수 있다. ReleaseGuard의 "판정과 사실은 규칙으로, 에이전트는 설명만"이라는 구조와도 맞는다.

"프롬프트에 skip을 고려하라고 지시하기"는 다음 후보이지만 추천하지 않는다. 결정적 코드로 되는 일을 LLM의 지시 준수에 맡기게 되고, 이번 결과상 효과도 보장되지 않는다.
