## 1. 결론

**판단: Go (2.1로).** 질문 1~3은 충족됐고, 4·5의 결과도 해석할 수 있는 형태로 모였다.

다만 이것은 **"붙일 수 있다"는 확인이지 "쓸모 있다"는 증거가 아니다.**
- 저장소 1개, 커밋 5개, mutant 40개의 작은 실험이다.
- SURVIVED 13개가 실제 테스트 부족인지, 동작이 같은 변형(동등 mutant)인지는 판정하지 않았다. 그것이 2.1의 질문이다.

## 2. 실행 조건

| 항목 | 값 |
|---|---|
| 도구 | Cosmic Ray 8.9.0 (`spikes/stage2_0/.venv`, `requirements.txt`). mutmut 3.8.1은 Windows에서 실행 거부 (WSL 요구) |
| 사용한 Cosmic Ray 기능 | `init`·`dump`(mutation 목록과 줄 위치), `apply`(한 mutant 적용). 테스트 실행·결과 판정은 어댑터가 직접 함 (JUnit으로 실패 종류를 구분하려고) |
| 쓰지 않은 기능 | `cr-filter-lines`: 모듈을 하나만 받는다 (`module-path`가 여러 개면 오류). 그래서 `dump` 결과에서 줄을 직접 골랐다 · `mutate-and-test`: 결과가 killed/survived뿐이라 실패 종류를 구분하지 못한다 |
| 대상 줄 | 커밋에서 바뀐 Python 소스 줄 중 테스트 context가 있는 줄 (covered, import 시점만 실행된 줄 제외) |
| 연산자 | 비교 경계·부정 쌍 10종 (`==`↔`!=`, `<`↔`<=`, `>`↔`>=`, `is`↔`is not`, `in`↔`not in`), `and`↔`or`, `not` 제거, 숫자 바꾸기, `True`↔`False` |
| 선택 규칙 | 커밋을 오래된 순으로, 커밋당 최대 8개, 한 줄에 하나(연산자 이름 순 첫 번째), 전체 40개에서 멈춤 |
| 실행 | mutant마다 (a) 그 줄을 실행한 테스트만 (b) 전체 테스트. 시간 상한 120초 |

**선택 규칙 보완 (기록)**: 설계에는 "커밋 3~5개"와 "시간순으로 40개가 찰 때까지"가 함께 있었다. 그런데 첫 커밋(`fc58c0e`) 한 파일에만 후보 줄이 95개라, 그대로 두면 40개가 한 커밋에 몰린다. 그래서 커밋당 8개·한 줄에 하나를 더했다. mutant 3개로 도구를 확인한 뒤, 본 실행 전에 **후보 줄 수만 보고** 정했다.

**연산자 필터가 꼭 필요하다**: Cosmic Ray가 파일 하나에 만드는 mutation은 모든 연산자 기준으로 326~1,019개였다. 비교 연산자 하나에 변형이 7개씩 생기기 때문이다.

### SURVIVED 13개 — 무엇이 안 잡혔는지 읽을 수 있는가

원래 줄과 바뀐 줄을 보면, 각 SURVIVED가 어떤 동작 변화를 테스트가 잡지 못했는지 읽을 수 있다. 아래는 **변형 종류로만** 묶은 것이다. 실제 테스트 부족인지 동등 mutant인지는 판정하지 않았다 (2.1).

| 종류 | mutant | 예 |
|---|---|---|
| 비교 경계 (`<`↔`<=`, `>`↔`>=`) | #13, #27, #28 | `s <= e < one_year_later` → `s < e < ...` |
| 숫자 상수 | #5, #7, #8, #26, #31, #38 | `min(years) + 1` → `+ 2` (조회 시작일), `indent=2` → `3` |
| 불리언 (`and`↔`or`) | #2, #23, #37 | `bool(z.namelist()) and z.testzip() is None` → `or` |
| 기본값 `False`→`True` | #39 | `setdefault("bs_section_confirmed", False)` → `True` |

- `#39`(`bs_section_confirmed` 기본값)와 `#13`·`#27`·`#28`(기간 경계)은 이 프로젝트의 원칙("미확인 값은 승격하지 않는다", 기간 판정)과 관련된 줄이다. 2.1에서 SZZ 결함 줄과 겹치는지 볼 후보다. **지금은 가설이다.**
- `#7`(JSON 들여쓰기)처럼 동작 차이가 사용자에게 의미 없을 수 있는 것도 있다. 이런 것을 걸러내지 못하면 SURVIVED가 그대로 소음이 된다.

### 관련 테스트만 vs 전체 — 40/40 일치의 의미

- 모두 일치했지만 강한 증거는 아니다.
  - Predict의 테스트는 서로 독립적이고, 공유 상태가 거의 없다.
  - 관련 테스트는 coverage context(그 줄을 실행한 테스트)에서 골랐다. 그래서 그 줄을 바꿨을 때 실패할 수 있는 테스트는 원리상 모두 포함된다.
- 불일치가 생길 수 있는 경우는 이 시험장에 없었다. 예: 모듈 import 시점에 실행되는 줄, 테스트 사이 공유 상태.
- 시간 절약은 중앙값 0.72초 vs 1.33초다. Predict의 전체 테스트가 원래 빠르기 때문에 차이가 작다.

## 4. 한계

- 저장소 1개, 커밋 5개(모두 초기 커밋), mutant 40개다. 비율을 일반화하지 않는다.
- SURVIVED의 유용성(실제 테스트 부족 vs 동등 mutant vs 의미 없는 변화)은 보지 않았다.
- `NumberReplacer`는 숫자 하나를 바꾸므로, 리스트 인덱스(`m[2]` → `m[3]`)처럼 의미가 크게 달라지는 변형과 사소한 변형이 섞인다.
- 한 줄에 하나만 골랐다. 같은 줄의 다른 연산자 결과는 모른다.
- 어댑터는 Windows 경로(`cosmic-ray.exe`)를 가정한다.
- 실패 메시지의 홈·임시 폴더 경로와 계정 이름은 결과 파일에서 가렸다 (`<home>`, `<tmp>`, `<user>`).

## 5. 2.1로 넘길 것

설계 6장·#11 8장의 계획을 이 결과로 구체화한다.

1. **SURVIVED 판정 기준**을 먼저 정한다 (결과를 보기 전에 고정). 실제 테스트 부족 / 동등 mutant / 의미 없는 변화를 무엇으로 나눌지.
2. **SZZ 연결**: 나중에 고쳐진 결함 줄 중 covered였던 줄(#3·#6의 41%)에 mutant를 만들어, SURVIVED가 결함 줄에 더 많이 나오는지 본다. coverage만으로는 못 본 것을 mutation이 보여주는지에 대한 직접 질문이다.
3. **행동 가능성**: SURVIVED에 테스트를 하나 추가하면 그 mutant가 KILLED가 되는지 (Actionable Survivor Rate).
4. **판정 불변**: mutation 결과는 `mutation_result`로만 둔다. 판정에 넣을지는 2.2에서 정한다.
5. 2.1에서 효과가 확인되지 않으면 2b로 간다 (Go/No-Go 원칙 유지).
