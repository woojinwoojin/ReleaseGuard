# Agent Eval 프로토콜 (Stage 1.6)

API를 호출하기 전에 고정한다. 결과를 본 뒤 기준을 바꾸면 보고서에 그 사실을 적는다.

## 질문

결정적 분석이 이미 찾은 검증 공백에 대해, 에이전트가 개발자가 실제로 쓸 수 있는 추가 정보를 만드는가?

결함 탐지율과 판정 정확도는 목표가 아니다. 에이전트는 판정에 들어가지 않는다. 8개 × 2회로 일반 성능을 주장하지 않고, 유지·수정·제외를 고를 근거만 만든다.

## 실행

- 사례: `eval/agent_cases.yaml` (공백 8개, 커밋이 겹치지 않음). `status: fixed`가 아니면 API를 부르지 않는다.
- 조건: 모델 스냅샷, 프롬프트·도구 해시, 상한을 결과 파일에 기록. 조건이 바뀌면 이어서 돌리지 않는다.
- 에이전트 입력에는 사례 유형·라벨·후속 수정 커밋을 넣지 않는다. 도구는 head 커밋만 읽는다.
- 기준선: 현재 프롬프트와 `run_loop` 그대로. 이번에 프롬프트·공백 선택 방식을 고치지 않는다.
- 온도는 지정하지 않는다. 응답 캐시를 쓰지 않는다. API의 프롬프트 캐시 할인은 비용 계산에 넣지 않는다.
- 순서: `--max-runs 2`로 사전 점검 → 나머지 14회. 사전 점검 2회도 16회에 포함.
- 상한: 요청 64회, 목표 $2, 추정 누적이 $5에 닿기 전 차단. 재시도 없음(`max_retries=0`), 요청 시간 120초.

고정 규칙:

- API 결과를 본 뒤 사례를 교체하거나 빼지 않는다. 실패도 결과에 넣는다.
- 사전 점검 뒤 프롬프트·모델을 고쳐야 하면 그 결과를 따로 보존하고, 고친 조건으로 새 출력 폴더에서 처음부터 시작한다.
- B1의 "skip이 원인"은 미확인 가설이다. 정답으로 쓰지 않고, 원인 확인은 별도 조사 결과로 적는다.
- 보고서에 적을 편향: week1 없음, 파일 전체가 공백인 사례를 뺐기 때문에 작은 공백에 치우침.

## 자동 지표

| 지표 | 뜻 |
|---|---|
| Structured Output Success | 스키마대로 답한 실행 비율 |
| Reference Validity | 인용한 파일·줄·도구 호출이 존재하는 비율. **설명이 맞다는 뜻이 아님** |
| Test Path Validity | 제안 파일이 테스트 분류 경로인지 |
| Tool Error Rate | 실패한 도구 호출 비율 |
| Cost / Latency | 실패 포함 요청 수, 토큰, 사용량 미확인 수, 추정 비용, 시간 |

## 사람 채점 (0·1·2, 점수마다 근거 한 줄)

| 항목 | 0 | 1 | 2 |
|---|---|---|---|
| Evidence Grounding | 인용한 내용이 설명을 뒷받침하지 않음 | 일부만 뒷받침 | 설명의 핵심을 뒷받침 |
| Behavior Accuracy | 틀렸거나 없는 동작을 말함 | 맞지만 핵심이 빠짐 | 바뀐 동작을 맞게 말함 |
| Trigger Accuracy | 그 조건으로 공백에 닿지 않음 | 닿지만 조건이 모호함 | 닿는 조건이 구체적 |
| Test Feasibility | 없는 API나 준비할 수 없는 입력에 의존 | 상당한 추측이나 준비가 필요 | 저장소의 형식으로 바로 쓸 수 있음 |
| Assertion Quality | 동작을 확인하지 않음 (실행만 함) | 약하게 확인 | 바뀐 동작을 구분해서 확인 |
| Repeat Consistency (사례별) | 두 실행의 핵심이 다름 | 설명은 같고 테스트가 다름 | 설명과 테스트 방향이 같음 |
| Added Value (사례별, 규칙 기준선과 비교) | 기준선을 다시 말함 | 약간의 정보 추가 | 직접 찾아야 했을 조건·입력을 제시 |

정상 변경 사례(N1~N3)는 **근거 없이 결함을 주장한 응답 수**도 센다. 후속 수정 사례(F1~F3)는 후속 수정 내용을 응답을 채점한 **뒤에** 열어서, 그 동작을 언급했는지 따로 적는다.

## Gap Closure (제안 3~4개)

설명 품질 평가에는 8개를 모두 넣는다. Gap Closure 대상은 결과를 보기 전에 정한 순서로 고른다.

- 사전 분류 (`gap_closure_class`): A = 함수를 직접 호출해 테스트 가능 (F1·F2·F3·N1·N2), B = 앱 런타임·스레드가 필요 (N3·B1·B2).
- 순서: **F3 → N2 → F1 → B2**, 예비 N1 → F2 → N3 → B1. 앞에서부터 4개를 시도한다.
- 건너뛰는 경우는 하나뿐이다: 두 실행의 Test Feasibility가 모두 0이면 예비로 넘어가고 이유를 적는다. 결과가 나쁘다는 이유로 건너뛰지 않는다.
- 두 실행 중 어느 쪽을 쓸지: 실행 1. 실행 1이 실패했거나 Test Feasibility 0이면 실행 2.
- 실행할 수 없는 제안은 "제안 품질"과 "Gap Closure"를 따로 기록한다.

| 수준 | 조건 |
|---|---|
| 실행 가능 | 테스트가 수집·실행됨 |
| Gap Closure | 대상 공백 줄을 실행함 (coverage로 확인) |
| 동작 검증 | assertion이 기대 동작을 확인함 (해당 줄을 바꾸면 테스트가 실패) |

- 대상 커밋의 임시 스냅샷에서만 실행한다. 사용자의 작업 폴더와 대상 저장소를 바꾸지 않는다.
- 사람이 테스트를 쓴다. 제안에서 바꾼 부분(줄 수, 이유)을 기록한다. 에이전트가 만든 코드를 자동 실행하지 않는다.

## 결과에 따른 다음 선택

| 결과 | 다음 |
|---|---|
| 설명이 맞고 테스트가 공백을 메움 | 단일 에이전트 유지 |
| 설명은 좋은데 테스트가 안 돌아감 | 테스트 제안 구조 개선 |
| 참조는 맞는데 설명이 틀림 | Context 구성과 근거 검증 개선 |
| 반복마다 크게 달라짐 | 모델·프롬프트 안정성 실험 |
| 규칙 기준선과 차이가 작음 | 에이전트 실행 범위 축소 |
| 비용이 효용보다 큼 | 호출 수·맥락 크기 축소 |

결과가 나빠도 곧바로 Multi-Agent나 RAG로 가지 않는다. 입력 부족, 검색 실패, 추론 오류, 테스트 작성 능력 중 어디가 원인인지 먼저 나눈다.
