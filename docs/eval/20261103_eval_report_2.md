# Eval 보고서 #2 — 위험 내용 대조와 반복 실행 일관성

작성: 2026-11-03 · 원본 결과: [20261103_eval_agent_x3_raw.md](20261103_eval_agent_x3_raw.md), [20261103_eval_agent_x3_raw.json](20261103_eval_agent_x3_raw.json) · 이전 보고서: [#1](20261103_eval_report.md)

보고서 #1의 개선안 1(HIGH 내용을 후속 수정과 대조)과 2(반복 실행 일관성)를 수행했다. 코드·프롬프트는 바꾸지 않고, Eval이 위험 내용과 사용한 도구를 저장하도록만 고친 뒤 라벨 있는 15개 커밋을 **3회씩(총 45회)** 돌렸다.

## 1. 요약

- **에이전트는 문제가 생길 "위치"는 절반 정도 짚지만, 무엇이 "틀렸는지"는 하나도 짚지 못했다.** 후속 수정 커밋 6개 중 3개에서 실제로 고쳐진 코드 영역을 위험으로 언급했지만, 실제 결함(미확인 값이 확정 값으로 승격됨, 누락 값을 0으로 읽음, 보고서가 근거보다 넓게 주장함)을 지적한 경우는 0건이었다.
- 에이전트가 낸 위험은 대부분 **"결과가 달라질 수 있다", "테스트가 없다", "실행이 중단될 수 있다"** 같은 일반적인 변화 경고였다. 이 프로젝트의 원칙(미확인 값은 승격하지 않는다)을 모르니, 그 원칙을 어기는 변경을 알아볼 수 없다.
- 후속 수정 커밋의 verified HIGH는 **실행 단위 0.333 (6/18)**, SAFE 커밋은 **0 (0/21)**. 헛경고는 3회 모두 없었다.
- **같은 커밋을 3번 돌리면 HIGH 여부가 15개 중 2개에서 달라졌다.** 1차 Eval과 비교하면 HIGH가 나온 커밋 자체가 바뀌었다 (`9e9c12b`·`b515f78` → `b67e806`·`3db2f31`).
- 판정은 15개 모두 3회 같았다. 다만 R07이 발동한 커밋은 이미 다른 규칙으로 REVIEW였기 때문이고, **에이전트가 판정을 안정적으로 만든 것은 아니다.**
- 보고서 #1의 가설 "문서·데이터 diff를 열어서 비용이 크다"는 **틀렸다.** 도구 호출 514회 중 데이터·문서 대상은 64회(12%). 비용은 소스 변경 커밋에서 도구 상한(20)까지 쓰거나 큰 범위를 `read_file`할 때 커진다.

## 2. 실행 설정

보고서 #1과 같다 (gpt-5.4-mini, reasoning low, LLM 최대 8회·도구 최대 20회, 수기 정답 15개). 차이는 반복 3회와, 결과에 위험 제목·설명·근거, 사용한 도구·인자를 저장한 것뿐이다.

**정정**: 보고서 #1은 후속 수정 커밋을 5개로 셌으나 `da30a78`(후속 수정 `c2fe0d1`)을 빠뜨렸다. 6개가 맞고, #1의 HIGH recall은 2/6(0.33)이다. #1 본문도 고쳤다.

## 3. 위험 내용 대조

후속 수정 커밋 메시지에 적힌 실제 결함과, 3회 실행에서 에이전트가 낸 HIGH·MEDIUM 위험을 대조했다.

- **영역 일치**: 실제로 고쳐진 코드 영역(같은 계정·같은 처리 경로)을 위험으로 언급함
- **결함 일치**: 무엇이 잘못됐는지(결함의 성격)까지 맞힘

| 커밋 | 실제 결함 (후속 수정에서) | 에이전트가 낸 관련 위험 | 영역 | 결함 |

**영역 일치 3/6, 결함 일치 0/6.**

SAFE 기대 커밋에서도 MEDIUM은 나왔다 (3회 합계). `99309f2` 7건(실행마다 2~3건), `c7733b3` 8건(2~3건), `f962d60` 1건(1회만). HIGH가 아니라서 판정에는 영향이 없지만, 사람이 보고서를 읽을 때는 경고가 많아 보인다.

### 왜 결함을 못 찾는가

1. **프로젝트 원칙을 모른다.** Predict_Success의 결함은 대부분 "미확인 값은 승격하지 않는다", "없는 값은 0이 아니다", "근거보다 넓게 주장하지 않는다" 같은 원칙(`docs/decisions.md`의 D1~D22)을 어긴 것이다. 에이전트에게는 코드와 diff만 있고 원칙 문서가 없다. 원칙이 없으면 "조건이 좁아졌다"(9e9c12b)처럼 오히려 안전하다고 읽는다.
2. **HIGH 기준이 모호하다.** 프롬프트의 HIGH는 "잘못된 결과·장애 가능성이 근거로 확인됨"인데, 실제로 나온 HIGH는 "결과가 달라질 수 있다"였다. 결과가 달라지는 건 변경의 목적이기도 하다.
3. 도구 상한(20)에 닿은 실행이 4회 있었다 (`3db2f31` 2회, `b67e806`, `c7733b3`). 탐색을 다 못 하고 답했을 수 있다.

1번이 제안서 Stage 3(Knowledge RAG)을 도입할 근거다. 지금 확인된 병목은 "코드를 못 읽는 것"이 아니라 "판단 기준이 될 문서가 없는 것"이다.

## 4. 반복 실행 일관성

| 지표 | 값 |
|---|---|

| 근거 확인 비율 | 0.951 (#1: 0.914) |

HIGH가 실행마다 달랐던 커밋:

| 커밋 | 실행 1 | 실행 2 | 실행 3 |
|---|---|---|---|
| `b67e806` | HIGH | - | HIGH |
| `adb2f5b` | - | - | HIGH |

1차 Eval(보고서 #1)과 비교하면 HIGH가 나온 커밋이 거의 겹치지 않는다.

| 커밋 | #1 (1회) | #2 (3회) |
|---|---|---|
| `9e9c12b` | HIGH | 0/3 |
| `b515f78` | HIGH | 0/3 |
| `adb2f5b` | HIGH | 1/3 |
| `3db2f31` | - | 3/3 |
| `b67e806` | - | 2/3 |

**에이전트의 HIGH는 아직 판정에 쓸 만큼 안정적이지 않다.** 지금은 R07이 이미 REVIEW인 커밋에서만 발동해서 판정이 흔들리지 않았지만, SAFE가 될 커밋에서 HIGH가 한 번씩 나오면 판정이 실행마다 달라진다.

## 7. 한계

- 결함 일치 판정은 후속 수정 커밋 메시지를 기준으로 사람(Claude)이 했다. 커밋 메시지에 없는 결함은 대조하지 못했다.
- 후속 수정 커밋 6개, 실행 3회. "결함 일치 0/6"은 작은 표본이지만 18회 실행 어디에서도 결함 수준의 지적이 없었다는 점은 분명하다.
- 대상 저장소가 하나이고, 그 저장소의 결함이 "원칙 위반" 유형에 몰려 있다. 다른 유형(크래시, API 깨짐)에 대한 에이전트 성능은 이 Eval로 알 수 없다.
