## 2. V1 — 정적 검사의 한계가 실제로 드러남

- 설계 2장은 "`app.py`에 최상위 이름 `api`가 없다"고 적었다. 이것은 **틀렸다**(P2). `app.py` 42줄에 `def api() -> ApiClient`가 있다(Streamlit 화면의 API 클라이언트 생성 함수). 설계를 쓸 때 `^api\b`로만 검색해 `def api`를 놓쳤다.
- 그래서 W05의 `app:api`는 **없는 이름이 아니라, ASGI 앱이 아닌 함수**를 가리킨다. 이름이 있는지만 보는 V1은 설계대로 `PASS`(defined_by: def)를 냈다.
- 결과에 맞춰 V1을 고치지 않았다. 객체가 ASGI 앱인지 판단하는 것은 정적으로 확정할 수 없는 영역이다(호출 결과, 데코레이터, 팩토리).
- **V1이 정상 사례에서 낸 FAIL은 0이다**(N0·N2·N3·DN1·DN2 모두 PASS, `python -m uvicorn` 형식도 해석). 하지만 이번 결함은 하나도 잡지 못했다. 그래서 V1이 V2를 대신할 수 있다는 근거는 없다. V1이 잡을 수 있는 결함(모듈 파일 없음, 이름 오타)은 이번 사례에 없었다.

## 3. V2 — 격리된 컨테이너 준비 확인

| 사례 | 결과 (3회) | 근거 |
|---|---|---|
| W05 | FAIL ×3 | 컨테이너는 계속 살아 있음. `/docs` HTTP 500, 30초 상한까지 실패. 로그: `asgi2.py` `self.app(scope)` → `TypeError: 'ApiClient' object is not callable` |
| W06·N0·N2·N3·DN1·DN2·CN1·CN2 | PASS ×3 | `localhost:8000/docs` 응답 (컨테이너 안에서 요청) |
| N1 | NOT_RUN ×3 | 그 커밋에 Dockerfile 없음 |

- **W05는 시작 실패가 아니라 "떠 있지만 준비되지 않음"이다**(P3, 설계 2장 정정). 프로세스 생존만 봤다면 W05는 통과했을 것이다. 외부 리뷰의 Q2 수정(15초 생존 → `STARTED_ONLY`, 실제 응답 확인)이 없었다면 W05를 놓쳤다.
- 격리 조건(`--network none`, `--cap-drop ALL`, `no-new-privileges`, 메모리 512MB·CPU 1·PID 256, 비밀값·볼륨 없음, `USER app`)에서 정상 사례가 모두 준비 상태가 됐다. 이 앱은 시작에 외부 네트워크·API 키가 필요 없다.
- 결정성: 사례 9개 모두 3회 결과가 같았다.
- 정리: 실행 전후 접두어 `rg2b0-` 컨테이너·이미지가 0개였고, 4주차 저장소의 HEAD·작업 트리도 그대로였다.

**비용** (27회, 이 기기):

| 항목 | 최소 | 중앙값 | 최대 |
|---|---|---|---|
| 콜드 빌드 (`--no-cache`, 9회) | 85.4초 | 97.7초 | 117.2초 |
| 캐시 빌드 (18회) | 5.8초 | 8.1초 | 11.3초 |
| 준비 확인 (PASS 24회) | 3.3초 | 5.5초 | 7.7초 |
| 1회 전체 (빌드+시작+확인+정리) | | 17.0초 | |

- W05처럼 준비되지 않는 경우는 준비 확인 상한(30초)을 다 쓴다.
- 캐시 빌드가 8초 안팎인 것으로 보아, 콜드 빌드 시간의 대부분은 의존성 설치 레이어로 보인다(의존성 9개, pandas·streamlit 포함). 레이어별 시간은 재지 않았다. 빌드에는 외부 네트워크를 썼다.
- 기본 이미지 다이제스트가 결과 파일에 빠졌다(P4). BuildKit이 기본 이미지를 빌드 캐시로만 받아 `docker image inspect`가 실패했기 때문이다. 같은 날 캐시 빌드 로그로 보충했다: `python:3.13-slim@sha256:e48f59cd…ee9ed90`. 실행 당시 해석된 값과 같다는 보장은 없다.
- 빌드 캐시는 지우지 않았다. 실행 뒤 전체 Build Cache는 11.65GB이고, 이번 실험분만의 크기는 따로 재지 않았다(P5).

## 4. V3 — CI 정책 검사

| 사례 | V3a 상대 | V3b 절대 | 근거 |
|---|---|---|---|
| W06 | FAIL | FAIL | base의 `test` / `Run tests` / `pytest -rs`가 head에 없음. 활성화된 pytest 단계 0개 |
| CN1 (단계 이름 변경) | PASS | PASS | 같은 명령이 남아 있음 → 이동·이름 변경으로 기록 |

| N1 (CI 추가 커밋) | NOT_RUN | PASS | 부모 커밋에 워크플로 없음 (비교 대상 없음) |
| 나머지 | PASS | PASS | |

- 비용: 사례당 0.03초 이하다(YAML 파싱만).
- **V3는 "단계가 있다"까지만 확인한다.** 그 단계가 실제로 실행됐는지는 확인하지 않는다. 이번 사례에서는 `if` 표현식, 경로 필터, 재사용 워크플로, `make test`·`tox`를 시험하지 않았다. 그래서 `INCONCLUSIVE` 경로는 한 번도 쓰이지 않았다.
- `pytest` 패턴은 이번 실험의 명시적 정책이다. 범용 기본값이라는 근거가 아니다.
- 이벤트 필터는 구현 때 해석을 정했다: push·pull_request 중 하나라도 필터 없이 테스트에 닿으면 PASS. 4주차의 push는 `branches: [main]`이지만 pull_request는 필터가 없다.
