## 1. 판정 — Stage 1 기술 MVP 완료, 제품 수준의 구분력 미검증

**달성:** Git 변경 수집·분류, Git snapshot pytest/coverage 실행, line/branch 근거, base/head 실패 비교, 결정적 규칙·scope, 공백 보고서, 선택적 단일 에이전트, 제안 검증, Seed·라벨·반복 평가가 작동한다. 기존 보고서에서는 58커밋 판정 불변, 19+6 Seed 회귀 통과를 기록했다.

**미달성/미확인:** (a) 코드 변경에 대한 리뷰 필요 여부 구분력, (b) 새·수정 테스트가 실제 수집·실행되지 않은 경계 상태, (c) 삭제의 영향 평가, (d) 다른 팀·언어·CI로의 일반화, (e) 테스트 실행 격리와 재현성, (f) Mutation의 추가 효용.

따라서 **Stage 1 종료는 '연구용 기술 MVP'의 종료이지, 머지를 자동 승인할 수 있는 제품의 검증 완료가 아니다.** 1차 사용자 산출물은 근거가 추적 가능한 **검증 공백 보고서**이며 SAFE / REVIEW REQUIRED / BLOCK은 **보수적 게이트**다. 'SAFE'는 버그 없음·배포 안전성·테스트의 의미적 충분성을 뜻하지 않는다.

## 2. 판정 성능 — 반드시 분모를 분리한다

| 집합 | 관측 결과 | 올바른 해석 |
|---|---:|---|
| 라벨 39개 전체: `need: yes`인데 SAFE | 0/20 | '검토 필요 라벨'에 대한 과소 경고. 실제 결함 검출률 100%가 아님 |
| 라벨 39개 전체: `need: no`인데 경고 | **11/19 = 57.9%** | 문서 전용 변경이 분모에 포함됨 |
| **라벨이 있는 정상 코드 변경만**: `need: no`인데 경고 | **11/12 = 91.7%** | 현재 코드 변경 판정의 낮은 구분력을 더 직접적으로 보여줌 |
| 58커밋 중 SAFE | 18/58 | 이 중 **17개는 문서만 변경**, 코드 변경 SAFE는 **1/41** |
| Seed 회귀 | Predict 19/19, week4 6/6 | 기존 규칙이 정해진 기대 결과를 재현한다는 근거; 일반화 성능이 아님 |

- `11/12`는 정상 코드 변경에 대한 **조건부 경고율**이다. 특정 학습용 저장소 집합의 작고 서로 연관된 표본이므로 일반적인 오탐률이나 결함 판별 성능을 뜻하지 않는다.
- 코드 변경 커밋 41개에서 SAFE가 1개뿐이라는 사실은 판정이 대부분을 REVIEW/BLOCK으로 분류한다는 뜻이다. 경고가 실제로 필요한지를 이 수치만으로 결정할 수는 없다.
- 경고 11건의 주된 원인은 G01 7, B03 1, scope_only 3. scope_only는 의도된 미지원 검증 정책으로, G01의 과잉 경고와 분리 평가해야 한다.
- 일부 `risky_area`가 별도 위험 규칙이 아니라 동반된 G01/B03 때문에 경고됐다. 따라서 과소 경고 0/20을 '위험 영역을 잘 인식한다'는 근거로 해석하면 안 된다.
- 0/20과 11/19의 Wilson 구간(독립 관측 단순 가정)은 각각 약 **0~16.1%**, **36.3~76.9%**. 같은 저장소에서 나온 커밋의 상관성 때문에 이 구간도 과도하게 낙관적일 수 있다.

**제품 해석:** 현재 ReleaseGuard의 검증 공백 데이터는 설명 가능한 정보이지만, 3단계 릴리즈 판정의 실제 구분력은 입증되지 않았다. Stage 2 Mutation이 이 문제를 자동으로 줄여 준다는 근거는 없다. Mutation 결과를 그대로 게이트에 추가하면 경고가 늘 수도 있다.

## 3. 임시 저장소에서 재현한 Stage 1.7 경계 사례 (`boundary_cases.sh`)

| 사례 | 실환경에 가까운 임시 Git 저장소 실행 결과 | 추천 정책 |
|---|---|---|
| 신규/변경된 테스트 파일의 수집 건수 0 | SAFE + COMPLETE | **T03 REVIEW** 후보 |
| 새로 추가한 테스트가 전부 skip | SAFE + COMPLETE; skip 목록만 출력 | **T03 REVIEW** 후보 |
| 유일한 테스트 파일 삭제로 suite가 `no_tests` | SAFE + COMPLETE | **T03 REVIEW** 후보 (삭제 정보 사용) |
| Python 소스 삭제만 있음 | SAFE + COMPLETE, N06 NOTE | **N06 NOTE 유지**, 향후 영향 분석은 별도 판단 |

**원인 경로 (코드 직접 대조):** `runner._run_once()`는 pytest exit code 5를 `no_tests`로 변환하고, 이때 `coverage={}`를 반환한다. `analyze()`는 `test_run["coverage"] = run.coverage is not None`으로 True를 기록한다. `decide()`는 이 불리언을 받아 실행 근거가 있다고 보고 E01을 발동하지 않는다. 테스트만 변경하거나 소스가 삭제돼서 새 소스 줄의 gap이 없다면 G01도 발생하지 않는다. `scope=COMPLETE`까지 나오는 이유다.

중요한 제한: **테스트 0개는 소스의 미실행 줄을 측정했다는 뜻으로도 유효하다.** 따라서 단순히 `no_tests` 전체를 E01로 바꾸면 기존 소스 변경 시의 G01 의미를 왜곡한다. `T03`은 **변경된 테스트를 실제로 수집·실행했는가**의 별도 계약으로 설계해야 한다.

소스 삭제의 경우 남은 코드가 삭제된 기호를 사용해도 반드시 테스트 실패가 발생하는 것은 아니다(경로 미실행, 동적 참조 등). 하지만 삭제를 모두 REVIEW로 바꾸는 근거 역시 없다. **N06을 NOTE로 유지하고, 삭제 후 정상/미참조/참조 오류 반례를 Seed로 추가하되 판정 변경은 보류**한다.

58커밋 중 N06은 0회이고 위 네 가지 경계 입력이 존재하지 않았다는 재집계 결과(`count_v17.py`)는, **기존 58개에 대해서는 새 규칙이 작동할 기회가 없었다**는 뜻이다. 과잉 경고가 미래에 늘지 않는다는 보장은 아니다. 반드시 정상·혼합 반례도 함께 평가한다.

## 4. 추가 코드 계약: coverage 버전과 node id

1. `runner.ensure_coverage()`는 `.rg/tools`의 패키지 디렉터리 유무만 검사한다. `analyze.test_run.record`는 요구한 상수 버전 문자열을 남길 뿐, 실제 실행된 coverage·pytest-cov 버전을 확인하지 않는다. Stage 1.7에서는 **실제 import 버전**과 요구 버전을 별도로 기록·검증하고, 불일치하면 미검증 상태로 처리한다.
2. `runner.parse_context()`는 `tests/x.py::test_a[case]`를 `tests/x.py::test_a`로 정규화한다. 함수별 보고서에는 유용하지만 Mutation이 선택 재실행할 때 파라미터를 구별하지 못한다. 기존 요약을 유지하고 **원본 parametrized node id**를 별도 저장한다.
3. 새로운 기록 항목은 환경 정보와 재현 근거만 포함하며 비밀값·호스트 환경 변수의 **값**을 기록하지 않는다.

## 5. Stage 1.7 실행 계약 (코드 변경 전 설계 후보)

| 작업 | 사전 확인할 조건 | 회귀 완료 기준 |
|---|---|---|
| T03: 수집 없음 | 변경된 테스트 파일 A/M이지만 수집된 테스트가 0건; rename·helper-only 변경은 별도 반례 | 경고는 테스트 파일/상태/수집 수 포함 |
| T03: 전부 Skip | 변경 테스트의 실행 대상이 모두 skip, 다른 파일의 pass로 가려지지 않음 | 대상 파일별 skip/수집 수 근거, 일부만 skip이면 무조건 T03 아님 |
| T03: 마지막 테스트 삭제 | 삭제된 테스트 파일과 `no_tests`가 동시에 발생 | 단순 기존 테스트 삭제+다른 테스트 계속 실행한 경우와 구분 |
| N06 | 기존 NOTE 유지 | SAFE/REVIEW가 자동으로 변화하지 않음; 불확실성 문서화 |
| coverage | 실제 런타임 버전 확인 | 정상/불일치/실패 버전 체크 테스트 |
| node id | 원본과 함수별 요약 동시 유지 | 매개변수 서로 다른 node id 충돌 없음 |
| 전체 회귀 | Seed + 경계 4개 + 정상 반례 + 기존 58개 | 의도한 변경만 기록, 원인별 판정·scope 별도 비교 |

- 단일 T03 ID를 쓰더라도 `reason_code`를 `COLLECTION_EMPTY`, `CHANGED_TESTS_ALL_SKIPPED`, `TEST_SUITE_REMOVED`처럼 나눠야 한다. 세 원인을 하나의 실패로 뭉개면 이후 독립 평가가 어려워진다.
- `scope=COMPLETE`와 `decision=REVIEW(T03)`의 병존 가능성을 설계에서 먼저 정의해야 한다. 현행 scope는 지원 파일 범위·실행 근거를 일부 혼합하므로 T03만 추가하는 것으로 의미 문제가 완전히 해결되는 것은 아니다. 이번 1.7은 원인을 분명히 보고하고, scope의 대대적 재설계는 별도 평가로 결정한다.
- **T03 반례:** 테스트 파일의 helper만 바뀜; 다른 파일의 테스트는 정상 실행; 신규 테스트 중 일부만 skip; 문서만 변경; 소스 추가만 있고 `no_tests`인 경우(G01은 유지); 테스트 파일 이름만 이동. 이 반례 없이 '모든 바뀐 테스트 파일에 수집 0개'만 적용하면 새로운 과잉 경고가 생길 수 있다.

## 7. 최종 결론과 남은 미확인 사항

- Stage 1은 **근거 중심 로컬 CLI 연구 MVP**로 종료한다. 실제 머지 자동 게이트용 품질을 보증하지 않는다.
- 두 추천 중 **T03(REVIEW) 후보 + 소스 삭제 N06 NOTE 유지**, **판정은 보수적 게이트이고 주된 가치가 공백 보고서라는 문서화**에 동의한다. 단, T03 세부 조건은 설계·반례로 확정 후 구현한다.
- `11/12`는 제품적 문제를 강하게 시사하지만 작은 관련 표본에서 나온 지표다. 별도 구분력 평가를 로드맵에 넣고, Stage 2.0은 제한적 기술 실험으로 진행한다.
- 상세 카운트와 경계 사례는 `20261111_explore/`의 스크립트로 로컬에서 재현할 수 있다. `out/eval/v17/`은 로컬 산출물이다.
